== Variables

// From Image 1.2 Programmer's Reference Guide, with slight rewording edits:

Within Image BBS, there are certain variables which can be considered "`reserved.`"
This does not mean that you cannot use them, __per se__, but that they can only be used for specific purposes:

* Some variables may be used any time, but have a specific purpose.
* Some variables can be used with certain subsystems, but not with others.
* Some variables may be used anywhere, but change continually.

This is explained in detail in the following paragraphs.

An example of a variable used for a specific purpose is `na$`.
This variable is used to print the handle of the user online.
Storing something for a module in this variable would cause an undesirable effect (modifying the user`'s handle).
Basically, these types of variables are used to control system statistics and are best left alone, only to be used to output information.

Some variables are used as interfaces between the BASIC and ML, an example being `pl`.
Setting `pl` to `0` will cause all user input to be in the form of upper- and lowercase characters.
When you set `pl` in BASIC, it causes the ML input routines to accept both uppercase and lowercase characters.

The main variables that can be used sometimes are arrays.
Depending on which subsystem you are in, the arrays may or may not be in use.
If they are not in use, it is safe to use them.
The only exceptions to this are `bf()`, `st()`, `dv%()` and `tt$()`.

* `bf()` holds the blocks free count for the system disks.

* `st()` holds the Board Activity Register stats; changing the values of this array should be reserved for updating the BAR stats.

* `dv%()` is the system device designator.
Altering this will change the device accessed by the system.

* `tt$()` cannot be used in a module that calls the editor, unless you want to edit existing text in that array.
All text stored in the editor is put into `tt$()`.

Some variables are intended to continually change.
These include variables that will print text to the screen and modem, as well as variables that form links between the BASIC and ML portions of the program.
Examples are `a$` and `an$`:

* When used in conjunction with `&`, the value of `a$` will be printed to the screen and modem.

* All responses entered at a prompt will be stored in `an$`.

These variables have a set purpose, but are intended to change.

=== Where the Variables Come From [[variables-dim]]

When the BBS boots, `im` line 3000 ``dim``s about 200 simple (non-array) variables in a fixed order, one line per letter (`dim a$,a%,ac%,am,ag$,...`, through `dim z$,z%,zz`).
Line 3070 then ``dim``s the arrays the BBS always keeps: `tt$(254)`, `dv%(36)`, `dr%(36)`, `co$(9)`, `hs$(10)`, `bf(6)`, `st(38)`, `im$(5)` and `pf$(10)`.

``dim``ming a simple variable just creates it, set to `0` or `""`.
Doing it at boot puts every reserved variable at the start of BASIC`'s variable table, in an order that never changes:

* BASIC finds a variable by searching the table from the start, so variables near the start are found sooner.

* The ML keeps the offsets of 50 variables (see <<ml-variables>>), worked out once by its start-up code, so those variables must exist before the ML first uses them and must never move.
Every variable a module creates later goes after them.

A few more arrays are only ``dim``med when a module needs them:
`im` line 306 (<<prg-im-routines.adoc#line-306,`gosub 304`>>, or `gosub 306` directly) ``dim``s the arrays Image 1.2 used (<<image-12-arrays>>).

The tables below list every variable `im` ``dim``s, plus a few others (marked ^†^) that `im` or the modules create when they first assign them.

These are the variables that <<prg-ampersand-calls.adoc#amp-9-bottom-variable,`&,9` Bottom Variable>> shows; its table lists all 50 numbers.

=== Variable

This is the variable`'s name.

=== Type

`BBS`: this is a BBS statistic or BBS-maintained variable, it could be saved to `e.data`.

`User`: this is a user statistic, saved to `u.config`.

`Work`: a scratch variable; modules use it for whatever they need at the moment.

`--`: nothing in 3.0 uses it (see <<unused-variables>>).

=== Use?

icon:check[role=green] indicates you can assign a value to it within your own modules.

icon:times-circle[role=red] indicates the variable is maintained by either the BBS ML or BASIC modules.
User data corruption or other unwanted side-effects may occur if this variable is reassigned.

icon:question[role=blue] means the variable may be used in some circumstances, but not in others.

=== Purpose

An explanation of what the variable does.

Records of `e.data` are listed in <<prg-file-formats.adoc#e-data,`e.data`>>.

=== Work Variables

The single-letter variables, `a$`-`z$` and `a%`-`z%`, are work variables used throughout the BBS by different subsections.
Most are free to use, but a few have a job:

* `a$`, `an$`, `b$`, `p$` and `w$` pass text to and from the ML (see <<strings>>).
* `a%` and `b%` pass numbers to and from the ML: most `&` calls that return a value put it in `a%`, and some take a second value in `b%`.
* `e%`, `e$`, `t%` and `s%` get the disk status (error number, message, track and sector) from <<prg-im-routines.adoc#line-5,`gosub 5`>> (`im` line 5, `input#15,e%,e$,t%,s%`).
Many routines test `e%` after opening a file.
* `r$` is a carriage return [`chr$(13)`]; never change it.
* `u$` was the command stack in Image 1.2; 3.0 uses `uu$` for that, and `u$` is a work variable.
* `x$` held the drive designators in Image 1.2; in 3.0 it is a work variable.
* `y%` and `z%` are used during boot: `y%` is the clock set method (`e.data` record 37), and `z%` holds the boot device number.
After boot they are work variables.
* `q$` is set by `im` line 90 to spaces, to center 40-column text on a wider screen.

The single-letter floating point variables (`a`, `b`, `x` and so on) are not ``dim``med; `im` and the modules use them as work variables too.
`x` is the record number for <<prg-im-routines.adoc#line-1,`gosub 1`>>, and `a` is the flag number and result for <<prg-im-routines.adoc#line-11,`gosub 11`>>.

=== Image 1.2 Arrays [[image-12-arrays]]

`im` line 306 ``dim``s these.
The sub-board, e-mail, General Files and network modules call it, and use the arrays as below; other modules may use them for anything (<<prg-ampersand-calls.adoc#table-array-numbers,array numbers>> for `&` calls that take an array).

[cols="1m,2"]
[%header]
|===
| Variable | Purpose

| bb$(31)
| Sub-board names of the current SIG (`i/MM.load`).

| dt$(61)
| `i.SB`: each post`'s date, then the date of its last response (11 digits each).
`i.EM` keeps the date of each letter in it; `i/NM.update` and `i/SM.reledit` keep network sub IDs in it.

| ed$(61)
| `i.SB`: each post`'s title.
`i.EM` also keeps a field of each letter in it.

| nn$(61)
| `i.SB`: who wrote each post: an account number, or `!` and a system ID for a network post.
`i.EM` also keeps a field of each letter in it.

| a%(61)
| Work array; `i/SM.reledit` and the `IM` editors use it.

| c%(61)
| `i.SB`: a number kept for each post, saved with it; `i/SM.reledit` uses it as a work array.

| d%(61)
| `i.SB`: number of responses to each post.
`i.EM` also keeps a number for each letter in it.

| e%(31)
| Record numbers in the sub-board file of the current SIG`'s boards (`i/MM.load`).

| f%(61)
| `i.EM`: a flag or count kept for each letter (`f%(0)` is the number of letters).

| ac%(31)
| Access group information: access mask of each board of the current SIG (`i/MM.load`).

| so%(31)
| Subop information: account number of each board`'s subop (`i/MM.load`).
